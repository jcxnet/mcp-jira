# Exploration: Rich styling for `mcp-jira setup` and `mcp-jira install`

Status: **success** — change `mcp-jira-rich-tui`, artifact store `hybrid` (Engram + openspec).

Scope note: Rich is used for **styling/formatting only** — not Textual, no widget
TUI. The widget route was decided against in the prior `mcp-jira-config-tui`
change (user decision, non-negotiable). All findings below were verified against
the repo and empirically against Rich 15.0.0 on Python 3.14.

## Current State

Both interactive commands are plain-text form loops with an injectable-prompt
architecture (lambdas for `prompt`/`hidden_prompt`/`select`/`confirm` so tests
run without a TTY):

- `src/mcp_jira/wizard.py` — `run_wizard()`: `input()`/`getpass.getpass` URL +
  hidden PAT, `select` for language (default `en`), `confirm` for read_only and
  the pre-write confirmation, `GET /rest/api/2/myself` connectivity check,
  0600 `os.open`+`os.chmod` write. All output is plain `print()` (stdout) and
  `print(..., file=sys.stderr)`. Non-TTY branch prints config path + guidance
  and exits 1. `^C` → "Aborted." on stderr, exit 1.
- `src/mcp_jira/installer.py` — `run_installer()`: same pattern; comma-number
  multi-select (empty = all), per-client merge with `.bak` backup + atomic
  rename + re-parse, plain `print()` summaries/status.
- `src/mcp_jira/cli.py` — dispatch only (`setup` → `run_wizard`,
  `install` → `run_installer`); server-start error printing is out of scope.
- **Dependency reality (verified in `uv.lock`)**: runtime deps are only
  `httpx` + `mcp`. `rich`/`markdown-it-py`/`mdurl` are NOT in the lock.
  `pygments 2.21.0` IS already locked — dev-only, pulled by pytest 9.1.1.
  Adding Rich brings `rich 15.0.0` (requires-python `>=3.9`, satisfies the
  project's `>=3.10`), `markdown-it-py`, `mdurl`, and promotes `pygments` into
  the runtime resolution (entry already exists in the lock). Lockfile impact:
  ~3 new package entries. Rich is pure-Python, no event loop — fits the plain
  terminal loop.
- **Test contract (verified by reading the suite)**: tests never assert on
  styled output; they assert substrings on plain output via `capsys`:
  wizard — `"Config written"` (out), `"Connection failed"`+`"AUTH_UNAUTHORIZED"`
  (err), `"required"` (err), `str(cfg)`+`"jira_url"` (out, non-TTY),
  `"Invalid URL"` (err), `"Aborted"` (err); also `_confirm_final_yes` matches
  `"Write config"` inside the confirm prompt text. installer — `"Registered
  mcp-jira in"`, `out.count("already registered") == 3`, `"Nothing to
  register."`, `"terminal"` (non-TTY), `"Aborted"` (err), `"nothing was
  written"` (err), `"not valid JSON"` (err), `FKEY not in out`. The injectable
  signatures are load-bearing: `(str)->str`, `(str, Sequence[str], str)->str`,
  `(str, bool)->str` for wizard; `(str)->str` confirm + `(str, Sequence[str],
  str)->str` targets_selected for installer.

## Affected Areas

- `src/mcp_jira/wizard.py` — all output sites (styling) + the 4 default prompt
  lambdas (Rich `Prompt`/`Confirm` if approach B); injectable signatures and
  prompt strings unchanged.
- `src/mcp_jira/installer.py` — output sites + default `targets_selected`/
  `confirm` lambdas; multi-select prompt and summary rendering.
- `pyproject.toml` — add `rich` to `[project].dependencies` (the only
  architectural change to the dependency contract).
- `uv.lock` — regenerated by `uv lock`; ~3 new entries (rich, markdown-it-py,
  mdurl; pygments entry already present).
- `tests/test_wizard.py`, `tests/test_installer.py` — must pass **unmodified**
  (verified possible); optionally gain new styling assertions later.
- Specs `server-config` (§setup-wizard, §wizard-testability) and
  `client-installer` (§testability) — no behavioral requirements change; the
  summary/confirmation/never-write semantics are preserved, only rendered
  differently.

## Approaches

1. **A: Rich Console for output styling only; prompts stay stdlib `input()`/`getpass`**
   - Pros: zero change to injection points and prompt text; smallest diff;
     delivers the visible win (styled errors, summary panel, success message,
     spinner during /myself); empirically zero test churn (see below).
   - Cons: prompt lines themselves stay plain (`input()` renders no choice
     highlighting, default hints, or inline re-prompt); less "wow" per prompt.
   - Effort: Low.

2. **B: A + Rich `Prompt.ask` / `Confirm.ask` as the *default* implementations
   behind the existing injectables** (lambdas adapted to the unchanged
   signatures)
   - Pros: prompts render `[en/es]` choices, `(en)` default, strip whitespace,
     re-prompt inline on invalid choice, `password=True` masking on TTY —
     verified behaviorally on Rich 15; tests still inject lambdas, so the
     suite is unaffected; wizard/installer validation loops remain as the
     fallback for injected callables.
   - Cons: `Confirm.ask` returns `bool` — the default wrapper must convert
     (`"y"`/`"n"`) to keep the `(str, bool)->str` contract; Rich's built-in
     choice validation replaces the wizard's own re-prompt messages for the
     defaults (behavior identical, message text differs — no test asserts the
     old messages); **markup gotcha**: prompt text containing `[` is mangled
     (verified: `[https://x]` was stripped from a prompt) — prompt strings must
     be escaped or kept bracket-free.
   - Effort: Medium.

3. **C: Full Rich form — panels/sections around every prompt**
   - Pros: most visually cohesive; every line styled.
   - Cons: heaviest churn on both files; panel-per-question adds vertical noise
     to a 5-question form; pushes toward the widget-TUI aesthetic the user
     rejected; largest surface for output drift.
   - Effort: High.

### Empirical evidence (Rich 15.0.0, pytest 9.1.1, fd capture)

- Rich `Console` output is captured by `capsys` and contains **no ANSI codes**
  under pytest — plain text, so every existing substring assertion holds.
  Verified for both a module-level `Console()` (pinned at import) and a lazily
  created one; `Console(stderr=True)` likewise. This holds regardless of
  `style=`/`Panel()` usage in the print calls.
- `Prompt.ask(choices=["en","es"], default="en")`: empty input → `"en"`;
  invalid input → re-prompts with Rich's own message; `"en "` → `"en"`
  (whitespace stripped). Maps cleanly onto the wizard's `select` semantics.
- `Confirm.ask(default=False)`: empty → `False`; `"y"` → `True`; invalid →
  `"Please enter Y or N"` re-prompt. Returns `bool`, not `str`.
- `Prompt.ask` reads via the builtin `input()` (`sys.stdin`), not the Console's
  `file` — irrelevant to the injectable design (tests never exercise the
  defaults), but means a single shared Console can serve prompts and output.
- Under a real non-TTY, `Prompt.ask(password=True)` degrades to getpass with an
  "echoed input" warning — harmless because the wizard guards `interactive`
  before ever prompting.

## Recommendation

**Approach B, scoped with A's discipline.** Use one shared Rich `Console` for
all interactive output: styled errors to stderr (`bold red`), a `Panel`-based
summary before the final confirmation, a styled success message, a spinner
around the `/myself` connectivity check, and a styled multi-select + summary in
the installer. Replace only the *default* prompt lambdas with thin Rich
adapters (`Prompt.ask`, `Prompt.ask(password=True)`, choices-validated select,
`Confirm.ask` → `"y"`/`"n"`), keeping every injectable signature byte-identical
and every prompt string unchanged (the `"Write config"` substring in the
confirmation prompt is load-bearing for `test_wizard._confirm_final_yes`).
Keep the non-TTY branch 100% plain `print()` — it is piped/scripted output and
tests assert on it directly. Add `rich>=13.7` (current: 15.0.0) to
`pyproject.toml`. If the user wants the absolute minimum diff, A alone still
delivers the visible styling win — B only adds the prompt-level polish on top.

## Risks

- **ANSI codes in non-TTY/piped output**: Rich auto-detects TTY and honors
  `NO_COLOR`; the non-TTY branch is left plain. Low.
- **Markup mangling of prompt text**: verified `[...]` is consumed as markup.
  Mitigation: escape prompt strings or keep them bracket-free (current prompts
  are; the confirmation prompt embeds a `path` — escape it). Low.
- **Behavior drift of validation loops**: with Rich defaults, invalid-input
  messages come from Rich, not the wizard loops; loops stay as fallback for
  injected callables. No test asserts the old messages. Low.
- **`Confirm` returns bool**: the default adapter must convert to the str
  contract or the production path breaks (tests inject strings and would not
  catch it). Low.
- **Scope creep toward a widget TUI**: keep the spec bound to "styled output +
  prompt polish"; no screens, layouts, or theme config. Matches the prior
  user decision. Medium.
- **Dependency footprint**: one new runtime dep (+2 transitive, 1 promoted);
  justified only if the styling is actually wanted — the stdlib-only route
  (prior change's choice) remains the zero-dep fallback. Medium (user call).

## Ready for Proposal

**Yes.** Tell the user: Rich adds a small, pure-Python runtime dependency
(rich + markdown-it-py + mdurl; pygments already in the dev lock) purely for
terminal styling — no Textual, no widgets, no event loop. The change is
confined to `wizard.py`/`installer.py` output and default prompt lambdas; the
injectable test contract is untouched and the 50 tests covering wizard +
installer + CLI + config keep passing unmodified (verified empirically). The
proposal should pick the polish level: styling-only (A, minimal diff) vs.
styling + Rich prompts (B, recommended). Non-goals stand: no Textual, no widget
TUI, no config-editing subcommand, no theme config.
